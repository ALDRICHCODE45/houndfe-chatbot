# Minimal checkout customer and address draft

Objective: prepare and confirm customer/delivery data without registering customers, changing saved addresses, creating orders or activating shipping.
Branch: `feat/minimal-checkout-customer-address` from `65e8434`; delivery: local work-unit commits only (no PR/push/deploy); review shape: feature-branch chain, explicit client T1 size exception (~1,280 authored lines); runner: direct installed Node/Jest binaries, isolated adapters and mocked HTTP/SDK.

## Specs

S1 — Customer/delivery lookup and draft. Owner: "creo yo que lo que debemos hacer es preguntarle sus datos al cliente (el chatbot) y en base a ello, revisar si ya existe una direccion asignada a ese cliente (tanto en el chat como en el sistema)". Use the trusted WhatsApp sender to resolve the customer. Offer saved addresses or collect new delivery data as a chatbot-owned draft. Chat history is not authoritative saved customer data. Check through the public client/service/SDK seams: unique, missing, ambiguous and failed lookup are distinct; only sender-owned saved addresses can be selected; malformed identities/arguments do not modify the draft.

A confirmed draft is not a created order or a confirmed final purchase. Tests assert zero forbidden calls and unchanged cart/sibling state.

S6 — Frozen read contract for S1, supplied by backend owner and accepted for continuation. Add `GET /chatbot-api/customers/checkout-context` with existing service auth and `customers:read`. Credential owns tenant; trusted chatbot application derives phone. Query: digit `phoneCountryCode` length 1–10; digit `phone` length 1–20; `limit` integer 1–20 default 10; optional UUID `afterAddressId` using the installed `@IsUUID()` all profile: case-insensitive RFC v1–v8 with standard variant, plus NIL/MAX; preserve supplied IDs verbatim. Invalid input is rejected, never silently clamped. Response is the exact `{status, customer, addresses, nextAfterAddressId}` envelope. `status` is `not_found`, `unique` or `ambiguous`; missing/ambiguous yield `customer:null`, `addresses:[]`, `nextAfterAddressId:null`. Unique customer is `{customerId,firstName,lastName}` with nullable lastName. Address fields are `{id,version,label,street,exteriorNumber,interiorNumber,zipCode,neighborhood,municipality,city,state,visualReferences,carrierPhone}`; street is non-null, other delivery fields nullable. `version` is an ISO updatedAt freshness marker, NOT a CAS-edit guarantee. Stable ascending `(createdAt,id)` cursor pagination reads limit+1; foreign/missing cursor returns 400 `INVALID_ADDRESS_CURSOR`. Existing GET/PUT/sales semantics remain untouched. Backend preserves existing credential-last-used/audit telemetry, but performs no business-data writes. New-route failure responses/audit messages must not expose phone/address payload from upstream read errors. Client tests cover valid discriminants, malformed responses, invalid query/cursor, scoped HTTP failures and existing transport behavior.
