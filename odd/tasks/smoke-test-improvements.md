# Production smoke test improvements (chatbot side)

Improvements the owner noted during the 2026-11-16 production smoke test on the Meta test number (Engram `smoke-test/production-improvement-notes`, decisions `smoke-test/improvement-decisions`). Branch: `feat/smoke-test-improvements`. Backend/frontend parts (catalog search matching, POS request context N2, detected receipt amount N9) were handed to the backend session; they are not in this document.

## Specs

- **S1 — Owner (verbatim):** "iniciemos con todas las mejoras que habiamos anotado anteriormente, bajemoslas bien primero y despues las implementamos." Order chosen: "Conversación primero" (N1, N4, N5, N7) → N11 search → technical.
- **S2 — N1 cart summary invites to continue.** Owner (verbatim): "Piensa en una persona hablando normalmente, el bot en este mensaje no te da siguientes pasos, solo te dice que se hizo". Decision: the cart summary (`minimal-cart.service.ts:658`, ends "No incluye envío y no reserva existencias. Todavía no se ha creado un pedido.") ends with `¿Desea agregar algo más o seguimos con su compra?` and two interactive reply buttons `Seguir con la compra` and `Agregar algo más`. usted/tú styling applies. Tapping `Seguir con la compra` behaves like the customer asking to buy (starts checkout: delivery data / shipping or pickup, exactly as "quiero comprar" does today); `Agregar algo más` invites them to say which product. Stale buttons (cart changed) follow the existing stale-button pattern.
- **S3 — N5 order summary.** The shipping cost / ETA appear once (today the shipping block "Su envío al código postal X no tiene costo. Llega en aproximadamente N día hábil." precedes a summary that repeats them: `minimal-catalog-agent.service.ts:532-536`, `domain/minimal-order-confirmation.ts:317-327`), and the summary always ends with `Total a pagar: $X MXN` (products + customer shipping charge; free shipping included) before the SÍ prompt (today only added when `customerChargeCents !== 0`, `minimal-order-confirmation.ts:330-336`). Pickup summaries keep their pickup text and also show `Total a pagar`.
- **S4 — N4 zone approved resumes checkout.** Owner (verbatim): "Pídame de nuevo el envío le pasa el trabajo al cliente". Decision: when staff approve a delivery zone, instead of `deliveryZoneResolvedText` (`delivery-zones/domain/delivery-zone-requester.ts:156`, "… Pídame de nuevo el envío y le muestro el costo actualizado."), the bot sends `¡Listo! Ya tenemos entrega a su código postal {cp}: {shipping sentence}.` and immediately re-quotes shipping and sends the order summary with the confirm button, only when the customer's confirmed delivery draft still has that ZIP and the cart is non-empty, inside the 24 h window, respecting the cart CAS writes. If any precondition fails (cart empty/changed, ZIP changed, quote fails, outside window), fall back to the current notice text without the resume. Rejected zones / CARRIER_ONLY keep their current behaviour.
- **S5 — N7 summary vs previous order.** "Muéstrame el resumen de mi pedido" (and similar: "mi resumen", "ver mi pedido") with a pending cart/summary re-shows the current summary (or cart), and with a recently placed sale shows that order (folio, total, payment status/next step); only "pedido anterior / la última vez / lo mismo que la vez pasada" uses `getLastOrder`. Fix the prompt overlap (`minimal-catalog-agent.service.ts:495`, `:1579-1581`, `:645`) and add a deterministic route in `handleTurn` when a pending summary or placed sale exists.
- **S6 — Paid orders.** When the receipt outcome poller observes a CONFIRMED receipt with `sale.debtCents === 0` (`receipt-media/domain/receipt-outcome.ts:91-96`), the bot marks the placed sale paid in the conversation state (`placedSale`, `minimal-cart.service.ts:32-49`, backward compatible). A paid placed sale no longer offers payment methods/details; a payment question answers that the order is already paid (reuse `Su pedido ya está pagado.` styling) and never creates a team request.
- **S7 — N11 search broadening (bot side).** When `searchCatalog` returns 0 results for a multi-word query, the bot retries automatically (bounded, e.g. at most 3 extra backend calls) with the significant words alone — dropping generic words like "croquetas", "alimento", "para", "de", "comida" — and merges results (dedupe by productId, keep backend order). The model is told when results came from a broadened search so it says e.g. "Croquetas Pedigree no tenemos; de Pedigree tenemos …". Port the "one broader refinement" guidance from the legacy sale-flow prompt to the minimal route. Out-of-stock matches are still shown as alternatives with their status.
- **S8 — Technical.** (a) `CONVERSATION_MIRROR_DELIVERY_ENABLED` is on for any value Joi accepts as true (`true`, `TRUE`, `True`, …) — configuration and validation agree (`configuration.ts:34`, `env.validation.ts:175`); same check for other boolean env flags read with `=== 'true'`. (b) The conversation mirror downloader logs a `warn` with the safe failure reason (same side channel as receipts) when a Meta media download fails; no URL/token/media id.
- **S9 — Compatibility and evidence.** Stored state written before this change keeps working. Every rule has a RED test first; existing behaviour touched (cart, checkout, shipping, receipt outcome) keeps its tests green. Docs describing changed replies are updated.
