## Behavior and safety contract

- Proposed route: `GET /internal/receipt-media/metrics`, protected by dedicated Bearer authentication. The path name is NOT proof of network privacy. Do not reuse Meta, backend, or capability secrets.
- `RECEIPT_MEDIA_METRICS_ENABLED` defaults false and is validated independently of receipt admission. Metrics disabled returns 404 without exposing metrics. Metrics enabled requires a valid dedicated `RECEIPT_MEDIA_METRICS_TOKEN` at boot, including when admission is disabled. Missing/invalid credentials return 401 with no metrics.
- Use a dedicated random opaque token: exactly 64 ASCII hexadecimal characters, generated from 32 random bytes (length/format validation is not an entropy guarantee). Validate the same contract in configuration and guard; preserve exact token bytes without normalization. Use strict Bearer credential handling and constant-time comparison of fixed-size digests. Require well-formed rawHeaders with exactly one Authorization field whose value matches the parsed single-string header; reject absent/empty/inconsistent metadata and duplicates even when parsed headers retain only the first. Malformed runtime values must yield 401, never TypeError. Accept tokens only through the Authorization header, never query parameters. Never expose tokens through logs, error messages, Joi contexts/original values, or metric labels. Do not add request logging.
- Preserve unrelated disabled receipt configuration permissiveness. Validate any supplied metrics token as exactly 64 ASCII hexadecimal characters even when metrics are disabled; disabled metrics must boot without a token. Configuration changes take effect through graceful restart, not live toggles.
- Use the installed `prom-client@15.1.3` with an explicitly isolated singleton Registry. No global registry, default/process collectors, duplicate registrations, or per-scrape database/provider calls.
- Implement the existing three-event `ReceiptTelemetryPort` contract with finite runtime-validated event/template allowlists. No IDs, PII, URLs, keys, tokens, captions, filenames, or arbitrary exception text. Telemetry failures must not break business operations.
- Deferred events remain absent/unemitted, not synthetic healthy zero activity. A minimal bounded configuration-state signal is permitted if needed to make the foundation useful; document explicitly that configuration is NOT evidence of functional ingestion or TX2 instrumentation. Do not expand the domain port or add new business emitters.
- Keep notification lifecycle behavior unchanged: enabled-only drain of already-committed intents, stable owner, existing polling floor and lease, fixed exhaustion log, and drain-before-pool-close. Do not start ingestion, wire ReceiptOutboxService/ReceiptTx2CommitPort, or produce intents. Do not change WhatsApp host production code.
- Disabled receipt access currently rejects lookup even though the route remains mounted. Do not promise that disabling admission preserves working receipt downloads or change that behavior in this unit.
- Runbook: scrape/auth/token rotation, TLS/network prerequisites, redaction, no-data/deferred interpretation, private bucket, capability-key retention/rotation, incomplete-multipart-only cleanup, growth, alerts, graceful drain/restart/disable, and no-POST unknown reconciliation. Distinguish implemented controls from future/staging drills. No production-readiness claim.
- Technical artifacts are English. No OpenSpec edits. No package/lock changes. Stop for genuine scope/security decisions rather than silently expanding.
