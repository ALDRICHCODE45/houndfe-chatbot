# Cart ambiguity binding

Objective: Bind cart presentations to verified product identities and preserve explicit quantity only within the same pending request.
Branch: feat/cart-ambiguity-binding (base 540a103). Delivery: local work-unit commits authorized by owner; push, merge and deployment NOT authorized. Runner: pnpm/Jest.

## Specs

S1. Treat ambiguity as normal input. Owner: "Si, por favor hermano, la verdad lo esta haciendo bien, y fui aumentando la \"ambiguedad\" de la conversacion, y ese tipo de ambiguedad va a ser el pan de cada dia en las conversaciones que tenga el bot." Resolve only verified product/presentation pairs; ask a focused clarification rather than invent identities. A presentation choice must not modify other saved lines.
S2. Reproduce the reported selection: "Agrega ibuprofeno de otra presentación", "Cuantas presentaciones tienes de ibuprofeno?", "Si, la de 500mg por favor." The final turn must not invent quantity or submit an unrelated variant. If quantity was never provided, ask for quantity without a cart write. Live logs currently show requested line 3 invalid_variant with catalog_match=false and stock_match=false; they do not prove where the UUID came from.
S3. Accepted quantity policy: "Agrega 2 ibuprofenos" followed by "Los de 500mg" retains two units from that same pending request. Owner acceptance: "Si hermano, estoy de acuerdo". Never inherit quantity from saved cart units or a pending request for another product. A new explicit quantity supersedes the prior pending quantity; a completed mutation must not leave an armed request that can run again.
S4. Preserve existing quantity meanings and successful behavior: "Agrega 5 unidades de croquetas nupec" is an addition, "Dejame solo una unidad de croquetas por favor." sets the total and repeating it does not increment, "Quita una unidad de croquetas" subtracts one, and "Agrega una unidad de Croquetas Nupec" adds one. Preserve valid variant selection, simple-product null transport, fresh stock/pricing checks, CAS, error replies, privacy and RESTOCK/EXPIRATION precedence. Reject an unverified reference/pair without writes; never weaken validation or automatically retry a quantity mutation.
S5. Verify through public SDK/cart interfaces with isolated in-memory data and offline OpenAI fetch where applicable. Tests must assert replies, quantities/totals, preservation of other lines, no write on clarification/rejection and no checkout calls. Update docs for the changed tool contract. Distinguish scripted tests from live model compliance; exact live UUID provenance and the NUPEC brand claim remain unproven and are not an authorization to alter catalog data.
S6. Keep changes within this chatbot's cart route. No backend changes, production requests, dependencies, migration, credential logging, legacy catalogReferences reuse, unrelated untracked edits or delivery. The durable cart format is unchanged; minimal-route conversational context may retain the existing in-memory/restart-loss boundary, documented honestly.

## Integration contract

- SDK cart mutations retain the names `setCartItem` and `adjustCartItem`, but take only `selectionRef`, nullable `quantity`/`delta`, nullable `quantityText` and required `continuation`. No model-provided cart UUIDs. Domain inputs, variant ownership, quoting, CAS and persisted cart remain unchanged.
- Catalog/stock/verified cart outputs expose `cartSelectionRef` for the product and each exact variant. Registration and snapshots are server-owned and sender-scoped. Session turns retain typed selection snapshots and pending intent even when the SDK response messages are discarded by the cart-reply branch.
- `prepareCartItem` takes `selectionRef`, `operation` (`add|set|subtract|remove`), nullable `quantity`, nullable `quantityText` and `continuation`. It records only grounded conversational intent, never calls a cart mutation, and supports preserving an explicit count before a presentation is selected. Instructions require preparation before asking for presentation when an explicit quantity was supplied.
- Caller supplies current text to grounding, not model-authored replacement text. Named whole-line removal may use optional server-trusted product/variant labels in the helper, never model-supplied labels; a partial count must still reject whole-line removal. This is a T3 compatibility extension and is covered by new RED tests.
- Clear pending intent after actual mutation attempts, and prevent automatic retry of an attempted adjustment within the SDK run. Clarification/preparation are not mutations. Expose pending intent in model instructions without trusting model-supplied snapshots. Missing quantity must produce a server-controlled quantity question and no write.
- Handle/document the 50-binding capacity with a bounded refreshed registry or safe clarification; do not silently evict a pending request into a different product. Unsupported count words clarify. Malformed cart-tool arguments and unknown references must not become unsupported customer acknowledgements.
- Public SDK regression tests use offline models/providers and isolated state. Parent observed RED job 14: both S2 missing-quantity and S3 same-request carry regressions fail on baseline (unsupported model acknowledgement, not the required server reply).
