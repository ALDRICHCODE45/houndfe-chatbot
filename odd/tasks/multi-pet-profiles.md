# Multi-pet customer profiles

Let a customer have more than one pet. Pet data lives in the backend (Customer → pets, visible in the POS); the chatbot asks which pet a request is for.
Coordination with the backend and frontend agents happens through intercom only (never read their repos). Bot contract: docs/contracts/customer-pets-bot-contract.md (read it before any chatbot task).

## Specs

- S1 Several pets per customer. Owner: "me gustaria analizar la posibilidad de que sea posible agregar mas de una mascota por cliente". Today the chatbot stores one pet and silently skips a second one (`petFactsConflict`, src/customer-profile/domain/pet-facts.ts:300).
- S2 Pets live in the backend. Owner answer: "En el backend (Customer → mascotas)".
- S3 Ask who a request is for. Owner example: "Claro que si!!, para quien son las croquetas? para max (labrador, adulto), o para bruno (chihuahua de 10 meses)?". Owner answer: "Pregunta siempre con botones (recomendado)".
- S4 History per pet. Owner selected: "Historial por mascota" («¿Lo mismo de siempre para Max?»).
- S5 Allergies and notes. Owner selected: "Alergias / notas" (warning, not a filter: the catalog has no ingredients).
- S6 Age that advances on its own. Owner selected: "Edad que avanza sola" (approximate birth date; suggests a stage change inside a conversation).
- S7 Forget one pet. Owner selected: "Olvidar una mascota" («Bruno ya no está» / «olvida a Bruno», with tact).
- S8 Prospects without a backend Customer. Owner answer: "Guardarlas local y subirlas al ser cliente (recomendado)" — the bot remembers pets from the first message; when the checkout creates the Customer, it uploads them to the backend and deletes the local copy.
- S9 Same product for two pets in one order. Owner answer: "Una sola línea sin mascota (recomendado)" — the backend rejects two lines of the same product/variant with different pets (or pet + no pet), so the bot sends one line without petId; per-pet history is lost only for that product.
