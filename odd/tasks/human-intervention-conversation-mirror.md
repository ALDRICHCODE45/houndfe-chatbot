# Human intervention — conversation mirror and media (backend unit 9)

Wire the chatbot's MESSAGE_MIRROR / MESSAGE_STATUS outbox rows to the backend unit 9 routes (messages:batch, statuses:batch, POST /media), so staff see the whole WhatsApp conversation in the inbox.
Contract: houndfe-backend `docs/chatbot-handoff/chatbot-requests-bot-contract.md` §"Conversation mirror and media (unit 9)" (:381-515, commit ed6fcd99). Branch: `feat/conversation-mirror`.

## Specs

- **S1 — Performance first (owner, verbatim):** "quiero que esto se haga bien, con calma, siempre teniendo como prioridad la performance del sistema, recuerda como esta desplegado esto, el chatbot en un server, el sistema(frontend/backend) en otro server de hostinger con especificaciones diferentes, hay siempre que tener en cuenta la performance de toda la comunicacion entre sistemas y de cada sistema en particular". Concretely: batch calls (≤50 messages, ≤100 statuses per call), one media upload per distinct file (idempotent keys, product photos reused across chats), never block the customer reply path on mirroring, bounded memory for media (stream, 10 MiB cap), and stay well under the shared `write` budget (300 requests / 60 s per credential, shared with requests create/cancel and feed outcomes).
- **S2 — Local is disposable (owner, verbatim):** "todo lo que tenemos localmente es DESECHABLE, no hace falta cuidar lo que tenemos en este entorno de desarrollo, no hace falta cuidar los datos, hacer respaldos, etc.. no importaa". Local/dev data needs no backups or preservation; migrations still must be correct for production.
- **S3 — Routes:** `POST /chatbot-api/conversations/:conversationRef/messages:batch` (scope `conversation:write`; 1–50 messages, array order = backend seq, all-or-nothing, idempotent by `waMessageId`; fields `waMessageId, direction IN|OUT, author?, type TEXT|IMAGE|STICKER|DOCUMENT|AUDIO|TEMPLATE|UNSUPPORTED, text ≤4096, mediaId (IMAGE/STICKER/DOCUMENT/AUDIO only), kind (UNSUPPORTED only: VIDEO|LOCATION|OTHER), providerTimestamp, observedAt`; `200 {accepted, duplicates}` both ACK). `POST /chatbot-api/messages/statuses:batch` (1–100 `{providerMessageId, status SENT|DELIVERED|READ|FAILED, occurredAt, errorCode?}`; `200 {applied, ignored, unknown[]}`). `POST /chatbot-api/media` (scope `media:write`, multipart one `file` ≤10 MiB, optional `sha256`, required `X-Idempotency-Key` lowercase UUID; sniffed types jpeg/png/webp/pdf/ogg/mpeg/mp4(m4a)/aac/amr; `201|200 {mediaId, mimeType, sizeBytes, sha256}`).
- **S4 — Error reactions (contract tables):** messages/statuses: `400`/`409 MESSAGE_ID_CONFLICT`/`422 MEDIA_TYPE_MISMATCH` → park and alert; `401`/`403` → stop and alert (do not kill rows); `413 BATCH_TOO_LARGE` → split and resend; `422 MEDIA_NOT_FOUND` → re-upload every media in the batch, resend the same batch; `429` → wait `Retry-After`; `5xx`/timeout → retry same body. Media: `400` park (sha mismatch → re-download); `409 IDEMPOTENCY_CONFLICT` → new key only if bytes differ; `413 MEDIA_TOO_LARGE`/`415` → no retry, mirror `UNSUPPORTED` (audio too large: also ask the customer to write); `503 MEDIA_STORAGE_FAILED` → retry same key.
- **S5 — Backend answers (2026-11-12, verbatim summary from the backend coordinator):** (1) outbound product photos: "fetch the bytes and upload via POST /chatbot-api/media with X-Idempotency-Key = UUIDv5(URL), then mirror OUT type IMAGE with that mediaId" (include a version/etag in the UUIDv5 input if a photo can change under the same URL); (2) interactive OUT: "type TEXT with the body text, and append the offered options as lines … e.g. "\n\nOpciones: Sí · No · Hablar con alguien" (button titles / list row titles, no payloads). Stay within 4096 chars (truncate options first)"; (3) inbound button/list replies: "TEXT with the chosen title as the customer saw it"; (4) `422 MEDIA_NOT_FOUND` does not name the item: re-upload every media in the batch, resend; (5) write budget 300/60 s per credential shared with requests create/cancel and feed outcome, raisable per credential; (6) messages:batch creates the conversation on a never-seen ref; (7) unknown status ids are harmless, retry after the mirror ACK, give up at 24 h; (8) inbound video/location: `UNSUPPORTED` with `kind` VIDEO|LOCATION, no text, no mediaId.
- **S6 — No phone in logs:** `conversationRef` (`wa:<wa_id>`) and the phone must stay out of logs and analytics (contract §common rules); mask as the existing `maskConversationRef` does (last 4 digits).
- **S7 — Audio (D13):** upload and mirror every voice note; when nobody is attending, also ask the customer to write it.
- **S8 — E2E:** once dev has unit 9 and the credential scopes, mirror a few messages including one image; the backend checks the staff read.
