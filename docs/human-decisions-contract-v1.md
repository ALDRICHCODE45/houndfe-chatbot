# Human decisions v1: RESTOCK (draft for peer vote)

**Status:** APPROVED DESIGN by the assigned backend and frontend agents; **not an existing API or authorization for their repository writes**. Each agent owns its repository and local authorization. The bot owns only its conversation and effect ledger. First demonstrable case: human-provided restock estimate; shipping approval is later only if it passes the same gates. Implementation-specific normalization, SQL concurrency and actual transport require tests before any runtime claim.

## One safe path

1. The bot durably reserves a stable `sourceRequestId` locally, then submits an idempotent RESTOCK request to the backend. It never says an advisor was contacted until backend intake and its own pending state are confirmed. It does not also open a separately actionable ops-WhatsApp handoff.
2. The backend owns a tenant-scoped PENDING decision. The POS reviewer sees a sanitized snapshot and chooses one typed action. A versioned, audited transaction records exactly one human resolution.
3. The bot polls for its resolution. It verifies its current pending marker, subject and human decision before applying; **both** RESTOCK outcomes must still be fresh. It records a local delivery attempt and reports a separate outcome. A human resolution alone never authorizes stock mutation or sale.
4. Customer messaging is a separate effect with its own failure/uncertainty handling. `RESOLVED`, a bot attempt, `PROVIDER_ACCEPTED`, and delivery to a customer's device are different facts. The UI says **“Respuesta registrada”** on human resolve, never “cliente notificado”. An ambiguous send is `DELIVERY_UNKNOWN`, not a safe automatic retry.

## State ownership

| Owner    | Authoritative fact                                                                        | Important limit                                                                                   |
| -------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Backend  | Decision request, tenant, reviewer, typed resolution, optimistic version, audit           | Has no transaction with bot conversation or Meta delivery.                                        |
| Bot      | Local request intent/pending identity, revalidation, application ledger, outbound attempt | Must not treat a provider send or a fake store as cross-store atomicity or exactly-once delivery. |
| Frontend | Display and commands only                                                                 | Never derives an action from free text or performs domain side effects.                           |

Backend RESTOCK persistence and API both use **`PENDING|RESOLVED`**; `resolution` is null iff PENDING and non-null iff RESOLVED. `REPORT_RESTOCK_ESTIMATE_UNAVAILABLE` is an informative resolution, **not** rejection. There is no request expiry or `EXPIRED` state in RESTOCK v1. `PENDING_DELIVERY|PROVIDER_ACCEPTED|DELIVERY_UNKNOWN|STALE` belongs to a separate bot outcome, not to the human decision or v1 FE projection. No `BLOCKED` collision row is created in v1; the existing shipping/receipt collision remains blocked in the bot.

## Proposed RESTOCK payloads

- Intake identity: fixed `source='houndfe-chatbot'` derived from the guarded route, `sourceRequestId` stable UUID supplied by the bot, tenant from `ServiceAuthGuard`. Unique `(tenantId, source, sourceRequestId)` survives credential rotation; submitting `credentialId` is audit-only. Existing `@IdempotencyKey()` reads `X-Idempotency-Key`; its UUID must equal body `sourceRequestId` or intake fails validation. New intake returns HTTP 201, exact replay HTTP 200 with the same full request; Nest needs an explicit scoped response-status path. Backend hashes a **canonical allowlisted** RESTOCK request: `(tenantId,source,sourceRequestId,type='RESTOCK',productId,normalizedProductName,variantId|null,sku|null,requestedQuantity|null,observedStockAtRequest|null,stockObservedAt|null,supersedesDecisionId|null)` with sorted keys, fixed UTF-8/number/ISO normalization and no unknown fields. Omitted nullable fields normalize to null; credential ID, server branch label, creation time and other projections are excluded. Exact retry returns the same request; same key with different canonical payload returns `409 IDEMPOTENCY_CONFLICT`. Source and tenant are never trusted from body.
- Immutable snapshot projection has **required keys**: `branchId` (tenant-derived), `branchName:string|null` (backend-derived), `productId`, `productName` (sanitized, bounded), `variantId:string|null`, `sku:string|null`, `requestedQuantity:number|null` (>0 if non-null), `observedStockAtRequest:number|null` (>=0 if non-null), `stockObservedAt:string|null` (canonical UTC ISO). `observedStockAtRequest` and `stockObservedAt` are both null or both present. Intake omits branch fields; backend supplies them. No raw customer phone, address, transcript, prompts, provider payloads, cost or arbitrary HTML/JSON. Bot keeps sender association locally. Intake `supersedesDecisionId:UUID|null` is null for the first request; when present backend requires same tenant/source and a prior durably STALE/reconciled outcome, never UNKNOWN. It participates in the intake hash. A nullable unique `(tenantId,source,supersedesDecisionId)` plus transactional predecessor eligibility prevents two concurrent successor requests for the same decision; nulls may repeat.
- RESTOCK request has no fixed `expiresAt` in v1. Bot still rejects a resolution if its local pending request or product identity has changed; backend may later add an explicit expiration policy without silently changing this case.
- Resolution is an **exact discriminated union**, not a free-text fallback:
  - `{action:'PROVIDE_RESTOCK_ESTIMATE', restockDays, expectedVersion, resolutionRequestId}`; `restockDays` is integer **1..365 natural days**, zero excluded.
  - `{action:'REPORT_RESTOCK_ESTIMATE_UNAVAILABLE', expectedVersion, resolutionRequestId}`; a `restockDays` field is forbidden. This means **no confirmed ETA**, not “will never be restocked”.
  - `resolutionRequestId` is a UUID generated once per logical reviewer attempt and reused after a timeout. Same ID + exact payload replays the committed result; same ID + different payload or a different attempt after resolution returns a stable `409`. `expectedVersion` prevents a losing reviewer from resolving.
- Resolution projection has exact variant keys: positive `{action:'PROVIDE_RESTOCK_ESTIMATE',restockDays,resolvedAt,resolvedBy:{id,displayName}}`, negative `{action:'REPORT_RESTOCK_ESTIMATE_UNAVAILABLE',resolvedAt,resolvedBy:{id,displayName}}` (no days). `resolvedAt` is server UTC; bot poll additionally returns `applyBefore=resolvedAt+1h` UTC. Decision `version=1` at intake and `version=2` after human resolve; ACK `expectedResolutionVersion=2` does not modify decision version. Exact resolve replay returns HTTP 200 and the same full detail projection. The positive action provides an estimate, not a guaranteed stock date; the negative action sends the customer “Por ahora no tenemos una fecha estimada de reposición.” The existing bot `NO_RESTOCK` wording is **not** reusable unchanged.

## RESTOCK v1 API contract (approved design, not implemented)

| Actor | Operation                                                                                                                      | Required authority                                                                                                               |
| ----- | ------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| Bot   | `POST /chatbot-api/human-decisions` (RESTOCK intake)                                                                           | ServiceCredential `human-decisions:create`; exact idempotent identity/hash.                                                      |
| Bot   | `GET /chatbot-api/human-decisions/:id` (poll); durable local intent retries POST with the same key to recover ambiguous intake | ServiceCredential `human-decisions:read`; tenant and source authorization.                                                       |
| Bot   | `POST /chatbot-api/human-decisions/:id/application-outcome`                                                                    | ServiceCredential `human-decisions:ack`; stable `attemptId` + expected resolution version + outcome/evidence; exact replay safe. |
| Human | `GET /human-decisions?status=PENDING&page=1&limit=20&search=&sortBy=createdAt&sortOrder=asc` and `GET /human-decisions/:id`    | JWT + tenant + `read:HumanDecision`; server pagination, stable `createdAt,id` order.                                             |
| Human | `POST /human-decisions/:id/resolve`                                                                                            | JWT + tenant + `update:HumanDecision`; exact action DTO, version/CAS, reviewer audit.                                            |

List accepts only `status=PENDING` in RESTOCK v1 and returns `{data,pagination:{pageIndex,pageSize,totalCount,pageCount}}`, `pageIndex` zero-based (request `page` one-based), default page size 20, allowed 20/50; optional `search` matches bounded product name only, `sortBy=createdAt`, stable `createdAt,id` order. Each item/detail is a **discriminated projection** with required `id,type:'RESTOCK',title,sanitizedSummary,createdAt,snapshot,version,status,resolution,allowedActions`: PENDING has `resolution:null`, `version:1` and allowedActions either the two exact RESTOCK codes (if reviewer has update permission) or `[]` (read-only); RESOLVED has a typed non-null resolution, `version:2` and `allowedActions:[]`. RESTOCK has no `expiresAt`. `GET detail` and successful/replayed `POST resolve` return the same full detail shape (HTTP 200). `allowedActions` are codes, never copy or a substitute for RBAC. Errors use `{statusCode:number,code:string,message:string}` with sanitized message: invalid input/query `400 VALIDATION_ERROR`, unauthorized `403 FORBIDDEN`, missing/cross-tenant `404 NOT_FOUND`, conflicts `409 VERSION_CONFLICT|ALREADY_RESOLVED|IDEMPOTENCY_CONFLICT`; FE refetches after 409, no embedded latest entity required. Backend's existing global filter/ValidationPipe do **not** emit this shape (`error,timestamp` and sometimes a message array); human-decision routes need a scoped filter/validation mapping with tests, without changing global API errors.

Human resolve changes only backend decision state. Bot outcome is separate: `PENDING_DELIVERY` before any ACK; `PROVIDER_ACCEPTED` needs a provider message ID and a bot-observed UTC `providerAcceptedObservedAt` **before** the deadline; `PROVIDER_ACCEPTED_LATE` records a definite provider acceptance observed at/after deadline; `DELIVERY_UNKNOWN` records an ambiguous attempt; `STALE` is allowed only when no send could have occurred. These are bot-reported facts, not independent proof of device delivery or of the backend clock. Backend stores its own `ackReceivedAt` separately. ACK `{attemptId,expectedResolutionVersion,outcome,providerMessageId?,providerAcceptedObservedAt?,attemptedAt?,evidenceCode?}` is one **terminal** outcome per request: backend hashes the canonical allowlisted evidence, exact replay of the same attempt ID/hash returns the same result, changed payload or second terminal attempt returns `409`. UNKNOWN and LATE enter a per-request `NEEDS_RECONCILIATION` hold: no automatic retry, late competing ACK or superseding decision, while other requests continue. Manual reconciliation is a distinct explicit/audited operation, not a silent overwrite; v1 may record and hold without implementing a resolution UI. If ACK/ledger cannot be implemented and tested, the demo is explicitly **“decision recorded + controlled polling”**, not a completed automatic handoff. A synchronous outbox emit is not delivery to the bot.

## Freshness and failure rules

- Owner-approved freshness for **both** actions: backend provides `applyBefore = resolvedAt + 1 hour` as UTC ISO; bot starts a send only if `resolvedAt <= now < applyBefore`. Positive estimate also requires `now < resolvedAt + restockDays * 24 hours`. Successful channel acceptance is recorded only when the bot observes a provider response with message ID and `providerAcceptedObservedAt < applyBefore`. This timestamp is the bot's observation, **not** the backend clock or device delivery; backend records `ackReceivedAt` independently. Never shift the advisor estimate to `applyAt` or promise an exact calendar date or guaranteed availability.
- After the deadline, record STALE only if a send definitely never started. A previously started attempt without a definite answer becomes `DELIVERY_UNKNOWN`; a definite provider acceptance observed at/after the deadline becomes `PROVIDER_ACCEPTED_LATE`. Neither may be relabelled STALE, retried or superseded automatically. A new correlated request (`supersedesDecisionId`) is allowed only after durable STALE or explicit audited reconciliation and actual new-request persistence.
- A failed intake leaves a durable local intent for an exact retry, not a false advisor notification. A failed poll/store/ACK/send is never presented as a completed application or notification. Neither store update nor Meta send is magically exactly-once.
- Old local ops handoff and new backend inbox must be mutually exclusive per request behind a default-off route selector. Shipping quotes remain disabled; no live backend/Meta/provider testing or deployment is authorized by this design.

## Frontend and review gates

Frontend owns a POS `Decisiones pendientes` server-paginated view (`useServerTable`), typed RESTOCK detail in one slideover, `allowedActions` registry, explicit confirmation, `409` refetch/read-only state, and safe text rendering. Register `HumanDecision` in **both** `AppSubject` and `APP_SUBJECTS` with a pin test; `read` and `update` are separate permissions. Positive UI copy: “Informar tiempo estimado” and “1 a 365 días naturales”; negative: “Sin fecha estimada”. No chat, raw JSON, HTML, bulk actions, WebSocket or receipt collision UI. The FE session remains read-only until its owner grants fresh local authorization.

**Offline exit tests:** tenant/permission isolation; exact and mismatched intake replay; two-reviewer CAS and ambiguous resolve retry; invalid days/negative extra field; old local pending identity and clock-stale result; repeated poll/ACK; store and send failures without false success; FE 403/409/refetch/mobile detail; no sale/stock mutation. One complete RESTOCK case is the meeting goal; shipping approval is conditional on equivalent proof. Neither a passing fake store nor a UI mock proves PostgreSQL race safety or live WhatsApp delivery.
